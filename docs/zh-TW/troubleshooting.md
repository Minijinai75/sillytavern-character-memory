# 疑難排解

從 CharMemory 統計欄中的**健康點**開始——它會執行自動檢查並告訴您出了什麼問題。如果點是綠色的，您的設定運作正常。如果是黃色或紅色，請點擊它跳轉到診斷以獲取逐項檢查明細。

---

## 健康檢查

健康點會根據可用資料執行最多 9 項檢查。檢查 1-7 在您開啟聊天時立即執行。檢查 8-9 在捕獲至少一次生成後執行。

| 檢查 | 檢查內容 | 狀態 |
|-------|-------------------|--------|
| **檔案已啟用** | 向量儲存中的「為檔案啟用」已開啟 | 如果關閉則為紅色 |
| **記憶檔案存在** | 角色的資料庫中有記憶檔案 | 如果缺失則為黃色 |
| **檔案已向量化** | 記憶檔案已建立索引（區塊數 > 0） | 如果為 0 個區塊則為黃色（在下次生成時解決） |
| **區塊重疊** | 向量儲存中的資料庫重疊設定 | 如果為 0% 則為黃色 |
| **區塊大小** | 向量儲存中的資料庫區塊大小與平均記憶區塊大小的比較 | 如果超出建議範圍則為黃色 |
| **檢索區塊** | 向量儲存每次查詢檢索的區塊數 | 如果 > 5 則為黃色（建議：2-3） |
| **分數閾值** | 檢索的最小相似度分數 | 如果未設定或太低則為黃色 |
| **記憶已注入** | 上次生成中出現的記憶項目 | 如果注入 0 個則為黃色（可能是正常的——分數閾值過濾） |
| **重複檢測** | 同一項目在注入內容中出現多次 | 如果發現重複則為黃色 |

### 修復每個問題

**紅色 — 檔案未啟用**
開啟 Extensions → Vector Storage → 在 File vectorization settings 下，勾選 **Enable for files**。

**紅色 — 未找到記憶檔案**
首先執行提取。記憶檔案在第一次成功提取時建立——點擊「立即提取」或等待自動提取觸發。

**黃色 — 檔案尚未向量化**
檔案存在但尚未建立索引。這在剛建立記憶檔案時是正常的——向量儲存會在下次生成時建立索引。只需發送一則訊息並生成回應。如果生成後檢查仍保持黃色，請檢查您的向量化來源是否已配置並正在回應。如果您最近清除了向量，請生成一則訊息以觸發重新索引。

**黃色 — 沒有注入記憶**
檔案存在且已向量化，但上次生成中出現了 0 個記憶。這可能是正常的——這意味著沒有記憶的分數高於當前對話主題的相關性閾值。如果您預期會注入記憶，請嘗試將向量儲存 → 資料庫檔案行中的分數閾值降低到 0.2。還要檢查 **Retrieve chunks** 是否未設定為 0。

**黃色 — 區塊重疊為 0%**
當重疊為 0% 時，落在區塊邊界上的記憶區塊會被分割——兩半都無法乾淨地檢索，您可能會在注入內容中看到重複的部分項目。0% 是一個有效的起點（特別是對於小型、帶主題標籤的區塊），但如果您在注入檢視器中注意到分割的區塊，請在向量儲存 → 資料庫檔案中將重疊增加到 10-15%。變更後[清除並重新向量化](retrieval-and-prompts.md#purge-and-re-vectorize)。

**黃色 — 區塊大小超出範圍**
太小：記憶區塊會跨區塊分割。太大：不相關的區塊共享一個嵌入，檢索失去精確度。請參閱[檢索與提示 → 建議設定](retrieval-and-prompts.md#recommended-settings)以獲取指導。

**黃色 — 注入內容中有重複項**
同一記憶項目在注入內容中出現多次。通常意味著一個區塊跨區塊邊界分割。增加區塊重疊和/或調整區塊大小，然後清除並重新向量化。

## 常見問題

**提取後顯示「0 個記憶」**
檢查活動日誌（點擊儀表板中的 **View full log**）。它會準確顯示發生了什麼——LLM 是否返回了 `NO_NEW_MEMORIES`、產生了無法解析的輸出，還是遇到了錯誤。在日誌中啟用 **Verbose** 以查看完整的提示和回應。

如果詳細模式顯示 `finish=length` 且使用了完成權杖但沒有內容，則您使用的是需要更高 **Max response length** 的推理/思考模型——在設定中增加到 2000-3000。

**記憶已提取但角色不記得它們**
向量儲存未配置，或「為檔案啟用」已關閉。檢查健康點——紅色表示有東西阻止了注入。開啟[檢索與提示](retrieval-and-prompts.md)並完成設定。

**提取從不自動觸發**
檢查面板中的 **Auto** 按鈕是否處於活動狀態（高亮顯示）。還要驗證統計欄中的訊息計數器是否正在遞增，以及冷卻計時器是否沒有阻止它。

**點擊「立即提取」時顯示「沒有未處理的訊息」**
所有訊息都已被提取。使用設定 → 重設 / 清除中的 **Reset Extraction State** 從頭重新讀取。

**記憶包含現有記憶中已有的事實**
提取提示會將現有記憶作為參考發送，並指示不要重複它們。如果模型一直這樣做，它可能太小而無法遵守邊界。切換到更大的模型——DeepSeek V3.1 或 GLM 4.7。

**記憶顛倒了誰做了什麼**
相同原因——模型太小無法準確理解。使用更大的模型。

**從長篇現有聊天中提取的記憶太稀疏**
一次批次提取數百輪對話時是預期的——LLM 一次只能看到一個區塊，無法判斷整個對話的重要性。CharMemory 在您聊天時增量提取效果最好。對於現有聊天，請嘗試將 **Messages per LLM call** 增加到 40-50 並重新執行批次提取。

**記憶太細緻 / 逐場景播放**
提示有項目符號限制和負面範例來防止這種情況。如果持續存在，請增加 **Messages per LLM call** 以為 LLM 提供更多上下文——更多訊息意味著它可以更好地判斷什麼是重要的與瑣碎的。

**檔案中累積重複記憶**
使用 **Consolidate** 來合併它們。為防止再次發生，請檢查[清除並重新向量化](retrieval-and-prompts.md#purge-and-re-vectorize)是否在重大記憶檔案變更後包含在您的工作流程中。

**記憶包含系統中繼資料、關係表或圖片提示**
CharMemory 在將訊息發送到 LLM 之前會剝離程式碼區塊、markdown 表格、`<details>` 部分和 HTML 標籤。如果中繼資料仍然洩漏，請編輯提取提示中的 **AVOID** 部分（設定 → 提示）。

## 診斷

點擊 CharMemory 面板標題中的**扳手圖示**以開啟疑難排解器，然後前往 **Diagnostics** 部分。生成訊息後點擊 **Refresh** 以捕獲當前狀態。

![診斷面板顯示記憶檔案狀態和健康檢查](../images/diagnostics.png)

診斷顯示：

- **記憶檔案** — 名稱、是否存在、項目和區塊數、向量化狀態和區塊數
- **已注入記憶 — 最後一次生成** — 為最近一次生成注入的確切項目。如果一個記憶存在但不在這裡，則它在語義上不夠相關以通過分數閾值，或者向量儲存設定需要調整。
- **角色知識書** — 綁定到此角色的知識書，包含條目數
- **已啟動條目 — 最後一次生成** — 基於關鍵字匹配實際觸發的知識書條目
- **擴充提示** — 所有擴充注入的原始內容，包括顯示向量儲存發送的所有內容的完整 `4_vectors_data_bank` 條目
- **注入健康** — 健康檢查卡，顯示每項檢查的狀態和建議

> **群組聊天注意事項**：診斷僅顯示第一個群組成員的資訊。要檢查特定角色，請使用 View / Edit，它會顯示所有成員。

## 重設工具

在設定 → 重設 / 清除中：

| 工具 | 作用 |
|------|------|
| **Reset Extraction State** | 清除「已處理」標記，讓您可以重新提取已提取過的訊息 |
| **Reset Batch Progress** | 清除所有聊天的批次提取進度追蹤器 |
| **Clear All Memories** | 刪除所有角色的所有記憶檔案和提取狀態。不可復原。 |

使用 Clear All Memories 前請備份您的資料庫檔案。

## 還是無法運作？

1. 開啟疑難排解器（扳手圖示）並運行診斷
2. 檢查活動日誌（詳細模式開啟）以獲取錯誤訊息
3. 閱讀[檢索與提示](retrieval-and-prompts.md)以獲取向量儲存調整指導
4. 在 [GitHub](https://github.com/bal-spec/sillytavern-character-memory/issues) 上提交 issue，附上診斷輸出和日誌摘錄
